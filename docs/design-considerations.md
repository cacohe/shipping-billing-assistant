# 业务与技术思考

1. **业务本质是受控的智能工作流，而不是高自治 Agent**
   处理步骤和输出边界明确：解析文件、抽取字段、校验、匹配账单、判断操作并生成固定 JSON。LLM 适合承担非结构化语义理解，应用工作流和领域规则负责财务决策。只有出现动态选工具、多轮补充信息或跨任务记忆等需求时，才值得引入更完整的 Agent Runtime。
2. **真正的难点是划清模型与确定性规则的边界**
   单据类型、费用描述和自然语言变更指令适合由模型理解；金额计算、币种合法性、账单匹配、字段继承和 AR/AP 判断需要可解释、可重复测试的规则。系统价值不在于“用了 LLM”，而在于把模型限制在它擅长且可校验的位置。
3. **输入质量决定效果上限，OCR 往往先于 LLM 成为瓶颈**
   邮件、表格、Word、文本型 PDF 和扫描件携带信息的方式不同，附件还可能互相补充。关键字段一旦在解析或 OCR 阶段丢失，后续模型无法可靠恢复。因此应分别观察解析、OCR、上下文组织和字段抽取质量，信息不足时保留为空并进入人工复核。
4. **账单匹配必须优先保证可追踪，而不是追求命中率**
   参考号、提单号、订舱号、箱号、交易方和金额都可能重复或缺失。匹配结果应记录命中规则与候选账单；多候选时停止自动更新。生产系统还应引入稳定账单 ID、版本状态和匹配置信度。
5. **高风险业务的目标是可控地减少人工工作**
   错误入账的成本通常高于一次人工复核。系统需要区分技术失败和业务不确定：外部服务不可用应重试或提示稍后处理；证据冲突、主体不明或无法判断 AR/AP 则属于正常待复核结果。评估指标应同时包含自动处理率、误入账率、复核率和平均处理时间。
6. **输入输出契约决定系统能否真正接入下游**
   演示输出强调逐费用项结果和审计理由；生产接口还需要稳定账单 ID、数量、单价、提单/箱号、字段级证据和金额精度约定。契约不完整时，即使抽取准确，下游也难以安全执行更新。
7. **从演示走向生产，需要补齐业务闭环而非简单增加基础设施**
   首先要明确谁提交、谁复核、谁批准以及结果如何回写 ERP；随后才是幂等、任务持久化、权限隔离、审计留痕、敏感文件生命周期和失败补偿。模型、提示词和 OCR 供应商升级还需要版本化脱敏评测集、回归和灰度验证。

## 当前演示范围的明确权衡

1. **输出保持最小稳定契约**：匹配账单 ID、数量、单价、箱号和提单号保留在内部模型或审计信息中，未作为平级输出字段。生产接入前应与下游重新确认契约。
2. **匹配规则保守执行**：规则按固定优先级运行；同一级命中多条时进入 `PENDING_REVIEW`，不随机选择，也不跳过高优先级候选寻找“看起来更合适”的结果。
3. **变更语义与数值比较分工**：LLM 识别材料是否明确要求修改；代码校验字段白名单、逐字段证据、新值和已有值。普通新单据不会仅因数值不同就被当作更新指令。
4. **PDF 同时保留 OCR 与文本层信息**：OCR 负责统一外部识别路径，有文本层时本地解析结果作为补充，代价是增加一次外部调用与临时存储步骤。
5. **URL 型 OCR 需要临时文件桥接**：本地文件短暂上传私有 Bucket，使用短期签名 URL，并在调用结束后立即尝试删除。生产环境还应增加生命周期策略和清理补偿任务。
6. **外部服务必须显式配置**：仓库不包含 OCR 地址或任何服务凭据；传输安全、可用性和识别能力由部署者选择的服务负责。
7. **金额内部精确、JSON 边界输出数字**：领域计算和比较使用 `Decimal`；对接真实财务接口时应进一步约定十进制定点字符串或带精度金额对象。
8. **实时模型效果不作为 CI 门禁**：CI 使用 OCR 和 LLM 测试替身验证规则、Schema 和调度；实时服务受网络、版本和模型漂移影响，应在独立的版本化评测流程中验证。
